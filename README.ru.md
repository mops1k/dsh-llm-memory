# dsh-llm-memory

[English](README.md) | **Русский**

Плагин долговременной слоистой памяти для
[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (dsh),
порт плагина `kilo-memory` из Kilo.

Плагин даёт агенту автономную слоистую память: записи хранятся как markdown-страницы
(источник правды), а поиск обеспечивает центральный FTS5-индекс на `node:sqlite`.
Плагин регистрирует семь инструментов для модели, добавляет инструкции по работе с
памятью в системный промпт, показывает WebUI-панель внутри оболочки dsh, выводит все
настройки отдельным пунктом Settings и умеет импортировать уже имеющуюся память из
других плагинов.

## Возможности

- **Семь инструментов для модели** с уникальными именами `llm_memory_*` (чтобы не
  конфликтовать с другими плагинами памяти):
  `llm_memory_recall`, `llm_memory_save`, `llm_memory_forget`,
  `llm_memory_delete`, `llm_memory_status`, `llm_memory_lint`, `llm_memory_heal`.
- **Автономная работа с памятью**: агент сам сохраняет записи, повышает tier
  (`normal`/`important`/`immutable`), помечает устаревшее забытым и удаляет — без
  запросов подтверждения. Опция `requireConfirmation` есть, но по умолчанию
  выключена.
- **Правило «забывать неактуальное»**: если пользователь изменил решение, прежняя
  запись помечается забытой/superseded, а не остаётся противоречием.
- **Слоистое markdown-хранилище** (источник правды) с центральным FTS5-индексом.
  Страницы разложены по категориям в подпапки `<kind>/`:
  ```
  <projectRoot>/.dsh/llm-memory/<kind>/<title-slug>-<id>.md       project + feedback
  ~/.dsh/llm-memory/_user/<kind>/<title-slug>-<id>.md             user (кросс-проектные)
  ~/.dsh/llm-memory/_db/memory.db                                 центральный FTS5-индекс
  ~/.dsh/llm-memory/_digest/<id>.md                               сырые дайджесты сессий
  ~/.dsh/llm-memory/projects.json                                 ключ проекта -> корень
  ~/.dsh/llm-memory/log.md
  ```
  Имя файла — `<title-slug>-<id>.md`, категория — имя подпапки (как в KiloCode:
  `pages/<kind>/<slug>.md`). Старые плоские файлы при старте мигрируют в `<kind>/`.
  Ключ проектных записей — **basename рабочего каталога сессии**
  (`dsh-llm-memory`, `plasma-keyboard`); ключ сопоставляется с абсолютным корнем
  через `projects.json` и реестр workspace'ов dsh, поэтому страницы попадают
  внутрь репозитория. Сессия без рабочего каталога использует заглушку `_no-cwd`.
- **Инкрементальное обновление индекса**: в FTS5-БД хранятся размер и mtime
  каждой страницы. Переиндексация (`llm_memory_heal`, старт после миграции
  плоской раскладки) перечитывает только новые и изменённые страницы —
  неизменённая стоит одного `stat`, а правка страницы вне плагина
  подхватывается следующим heal. Стоимость по каждому корню показывает
  `scripts/bench-index.mjs` (важно на медленных монтированиях вроде WSL `/mnt/c`).
- **Scoped-ограничения для lite-пресета**: пресет может импортировать
  `dsh-llm-memory/tool-restrict`, чтобы скрыть delete/status/lint/heal; full-пресет,
  WebUI и API сохраняют все семь глобально зарегистрированных инструментов.
- **Инструкции в системном промпте**: текст добавляется отдельной секцией и
  редактируется в настройках (по умолчанию — английский).
- **Отдельный пункт настроек**: **Settings → LLM Memory** содержит изменяемые
  во время работы опции, в том числе системный промпт, а также кнопки
  **Save settings**, **Import memory** и **Export rules to dsh AGENTS.md**.
- **WebUI-панель в оболочке dsh**: вкладка **LLM Memory** рядом с разговором
  рендерит WebUI как React-представление прямо в оболочке (без iframe) и следует
  светлой/тёмной теме dsh через дизайн-токены `--dsw-*`. На странице — разделы
  Search & Browse, Create/Edit, Graph, Status, Lint и Health (lint/heal).
  Та же страница по-прежнему доступна отдельно по HTTP-пути плагина
  (`<webPath>/ui`) и использует те же токены.
- **Импортёры** (идемпотентные, по внешнему ключу):
  - `kilo-memory` — `~/.config/kilo/memory/db/memory.db` (только чтение),
  - `dsh-mnemon` — `~/.mnemon/data/*/mnemon.db` (только чтение),
  - `dsh-memory` — SQLite-хранилище плагина (`~/.dsh/memory/memory.db`, таблица
    `memories(id, text, tags, pinned, created_at, updated_at)`, только чтение)
    и, для старых раскладок, markdown-файлы с заголовком
    `<!-- dsh-memory: {...} -->`. У плагина одна база на машину, поэтому его
    записи импортируются в кросс-проектный слой `user`; записи с `pinned`
    становятся `tier: important` с важностью 5.
  Корни источников определяются автоматически на Windows, в WSL (`/mnt/<drive>/Users/*`) и
  Linux; дополнительные пути задаются в `importRoots`. Импортированные проекты
  регистрируются как **воркспейсы dsh** (если их корневой путь существует).
- **Экспорт правил** в глобальный `$DSH_HOME/AGENTS.md`:
  - сначала **предпросмотр** (цель, режим, источники, полный текст блока), затем
    подтверждение;
  - идемпотентный управляемый блок — все прежние блоки схлопываются в один;
  - кнопка **неактивна**, пока экспортированный блок совпадает с источниками;
  - источник по умолчанию — **канонические зашитые английские правила** (`rules/en/AGENTS.md`),
    в которые перенесены уникальные immutable clauses;
    режим `rulesSource: kilo-verbatim` по-прежнему копирует оба файла Kilo как есть.
  Файлы Kilo при этом только читаются.

## Установка

```sh
# сначала удалить из профиля другой плагин памяти (например dsh-mnemon)
dsh plugin --profile web remove dsh-mnemon
dsh plugin --profile web add /path/to/dsh-llm-memory
dsh --profile web --dump-config   # строка плагина должна присутствовать
```

Пакет содержит bundle-patch (`cordis.patch.yml`) и браузерный клиент
(`lib/client.js`), поэтому реконсилер сам добавляет плагин в `dsh.profile.bundles`.
После установки перезапустите dsh.

Плагин объявляет две необязательные зависимости (`optionalDependencies`):
`@huggingface/transformers` (локальная модель эмбеддингов) и `sqlite-vec`
(векторный индекс в SQL). Если менеджер пакетов их пропустил, добавьте вручную:

```sh
cd ~/.dsh/profiles/web && pnpm add @huggingface/transformers sqlite-vec
```

При первом семантическом запросе модель `Xenova/multilingual-e5-small` (~120 МБ)
скачивается в `<storageRoot>/_models` (то есть `~/.dsh/llm-memory/_models`).
Без этих зависимостей плагин работает как раньше — на FTS5.

## Настройки

Откройте **Settings → LLM Memory**. Значения применяются после перезапуска плагина.

Поля схемы помечены `volatile()` — это условие dsh: страница настроек собирается
только из volatile-полей, остальные живут лишь в профильном патче. Значения таких
полей cordis отдаёт реактивными обёртками, поэтому плагин разворачивает их
(`unwrapSettings`) на входе в `apply` и дальше работает с обычными данными.

Настройки эмбеддингов лежат **плоско** (`embeddingsProvider`, `embeddingsDim`, …),
а не вложенной группой: редактор рисует только листовые поля схемы и вложенный
объект не показывает (проверено на живой панели 15.10.2026). В ядровый вид
(`embeddings: { provider, dim, … }`) их складывает `toMemoryConfig`.

| Опция | По умолчанию | Описание |
| --- | --- | --- |
| `storageRoot` | `$DSH_HOME/llm-memory` | Корень хранилища (пусто — по умолчанию). |
| `recallLimit` | `10` | Максимум записей, возвращаемых `llm_memory_recall`. |
| `promptRulesLimit` | `6` | Максимум строк правил/предпочтений в системном промпте. Дайджест входит в каждый запрос, поэтому держите его коротким. |
| `rulesPromptScope` | `project` | Охват дайджеста по проектам: `project` — кросс-проектный слой `user` плюс текущий воркспейс, `all` — все проекты. |
| `recallScope` | `project` | Область поиска по умолчанию: `project` — проект сессии плюс кросс-проектный слой `user`; `user` — только user; `all` — все проекты. |
| `autonomous` | `true` | Агент управляет памятью без запросов. |
| `requireConfirmation` | `false` | Спрашивать перед необратимыми операциями. |
| `systemPrompt` | встроенный (английский) | Инструкции, добавляемые в системный промпт агента. |
| `importRoots` | `[]` | Дополнительные каталоги для поиска памяти других плагинов. |
| `importAutoDetect` | `true` | Автоопределение корней на Windows/WSL/Linux. |
| `lintOverlapMinCommonWords` | `8` | Порог пересечения слов для отчёта lint. |
| `lintMaxPairs` | `200` | Максимум пар, проверяемых lint (0 — без лимита). |
| `webPath` | `/llm-memory` | Базовый HTTP-путь для WebUI и API. |
| `rulesSource` | `bundled-en` | Источник правил для экспорта: канонический bundled AGENTS.md или `kilo-verbatim` (оба исходных файла). |
| `embeddingsProvider` | `local` | Источник эмбеддингов: `off` — только лексический FTS5, `local` — локальная мультиязычная модель, `http` — зарезервировано (пока не реализовано). |
| `embeddingsModel` | `Xenova/multilingual-e5-small` | Модель эмбеддингов (для `local` — id модели transformers.js). |
| `embeddingsDim` | `384` | Размерность вектора; векторы другой длины пересчитываются. |
| `embeddingsBackend` | `js` | Где ищутся соседи: `js` — скан в процессе, `sqlite-vec` — KNN в SQL (нужен пакет `sqlite-vec`), `off` — выключено. |
| `embeddingsQuantization` | `float` | Точность хранения в `sqlite-vec`: `float`, `int8` (вчетверо меньше) или `bit` (в 32 раза меньше, но заметно теряет качество). |
| `embeddingsTopK` | `50` | Сколько чанков даёт векторная нога до слияния с FTS5. |
| `embeddingsMinScore` | `0` | Минимальный косинус попадания; косинус e5 сжат, поэтому надёжнее оставить 0 и полагаться на ранжирование. |
| `embeddingsBatchSize` | `16` | Текстов на один вызов модели при индексации. |
| `embeddingsChunkChars` | `800` | Целевой размер чанка в символах. |
| `embeddingsChunkOverlap` | `120` | Перекрытие соседних чанков (не больше половины размера чанка). |
| `embeddingsSemanticEdgesPerEntry` | `3` | Сколько семантических соседей на запись попадает в граф Wiki. |
| `embeddingsSemanticMaxEdges` | `300` | Общий предел таких рёбер. |
| `embeddingsPrewarm` | `true` | Грузить модель в фоне при старте, а не на первом запросе. |

### Startup-only опция профиля

Карточка Settings намеренно не содержит `sessionStartGuide`. Задайте её в patch профиля,
если подробная system-prompt секция присутствует всегда:

```yaml
- id: dsh-llm-memory
  config:
    sessionStartGuide: false
```

перезагрузите/перезапустите плагин профиля, чтобы listener был создан заново. Live patch
reload может сделать это автоматически, но уже работающий плагин не меняет listener на
месте. В остальных профилях сохраняется совместимое значение `true`.

## Совместимость при обновлении DSH

Начиная с DSH 0.2.0-rc.2 загрузчик профиля пропускает бандл целиком, если его
peerDependencies вида `@deepseek-ai/dsh*` не удовлетворяют текущему runtime
(`evaluatePluginCompatibility` в `@deepseek-ai/dsh-app-boot`) — плагин молча
исчезает из сессии. Поэтому все DSH-peer объявлены как `workspace:^` (загрузчик
всегда читает это как текущий runtime), а `scripts/check-dsh-compat.mjs`
проверяет и peer-диапазоны, и рантайм-символы, которые использует плагин.

После каждого обновления DSH:

```sh
pnpm check:dsh     # peer-диапазоны + рантайм-символы
pnpm run typecheck
pnpm test
```

Затем перезапустить DSH.

## Заметки и ограничения

- Память хранится в каталоге dsh и внутри каждого проекта
  (`<project>/.dsh/llm-memory/`) — отдельно от Kilo и от плагина
  `dsh-memory` (`~/.dsh/memory`), поэтому они могут существовать одновременно.
- Конфиг Kilo никогда не изменяется; sqlite-источники открываются только на чтение
  (при наличии WAL используется снимок `immutable=1`).
- `node:sqlite` синхронный, поэтому у хранилища один владелец на процесс.
- Изменения `storageRoot` и `webPath` вступают в силу после перезапуска плагина.
- `llm_memory_recall` по умолчанию ищет в текущем проекте плюс кросс-проектный
  слой `user`; чтобы искать во всех проектах, передайте `scope: all`.
- Несколько одновременно запущенных экземпляров dsh могут перезаписывать одно и то
  же состояние — держите один процесс. После жёсткой остановки удалите stale-lock
  `~/.dsh/.credentials.yaml.lock`, если следующий запуск не стартует.

## Семантический поиск (векторный RAG)

Поиск памяти сливает три ноги через Reciprocal Rank Fusion: FTS5 (BM25),
метаданные записи и косинус по векторам чанков. Метаданные весят меньше
остальных ног (0.1): они не зависят от запроса и работают как тай-брейкер —
замер на живом хранилище показал, что при весе 1.0 они вытесняли релевантные
попадания.

Как это устроено:

- Эмбеддинги считает локальная модель `Xenova/multilingual-e5-small` (384
  измерения, q8) через `@huggingface/transformers`; модель кэшируется в
  `<storageRoot>/_models`, API-ключи и сеть после первой загрузки не нужны.
- Инференс ONNX не отдаёт цикл событий (замер: батч 64 текста — 3.4 с и один тик
  таймера), поэтому индексация идёт в worker-потоке и не блокирует dsh; запрос
  эмбеддится на месте (~19 мс).
- Страницы режутся на чанки по предложениям (`chunkChars`/`chunkOverlap`); текст
  чанка для модели — заголовок плюс тело, а идентичность чанка — хэш текста и
  модели, поэтому неизменившиеся чанки не переэмбеддиваются, а смена модели
  инвалидирует векторы автоматически.
- Векторы лежат в таблице `memory_vectors` (канонический float32-кэш). Бэкенд
  `sqlite-vec` дополнительно зеркалит их в `vec0`-таблицу: KNN в SQL, фильтры по
  проекту/области/виду/уровню/статусу, опциональное квантование.
- Смена бэкенда ничего не переэмбеддирует — производная таблица поднимается из
  кэша; смена модели переэмбеддит записи.

Замеры 15.10.2026 (WSL2, Linux x64, Node v24.20.0, CPU), копия живой базы —
1059 записей, 3217 чанков × 384 измерения:

| Что | Значение |
| --- | --- |
| Поиск в процессе (`js`) | 24.0 мс среднее, p95 49.4 мс |
| `sqlite-vec` float | 11.6 мс, p95 22.1 мс, 100 % совпадения с `js`, 4.71 МБ |
| `sqlite-vec` int8 | 5.0 мс, p95 8.8 мс, 94.3 % совпадения, 1.18 МБ |
| `sqlite-vec` bit | 1.8 мс, 39.6 % совпадения, 0.15 МБ (экспертный режим) |
| Бэкфилл существующего хранилища | 1056 записей → 3210 чанков, 4.70 МБ, около 9 минут на CPU |
| Recall, self-retrieval hit@1 / hit@5 (40 сэмплов, k=5) | лексика 70 % / 100 %, гибрид 92.5 % / 100 % |

Полезные скрипты (нужен `pnpm build`):

```sh
# наполнить векторы у хранилища, созданного до RAG (на копии базы)
node scripts/backfill-vectors.mjs --copy --keep
# сравнить бэкенды и квантование
node scripts/bench-vector.mjs --root /tmp/llm-memory-backfill-XXXX
# сравнить лексическую и семантическую выдачу
node scripts/bench-recall.mjs --root /tmp/llm-memory-backfill-XXXX --samples 40
```

Что даёт семантика, помимо recall:

- `detail: "excerpt"` в `llm_memory_recall` возвращает пассаж, который сматчила
  векторная нога, а не начало записи (тот же бюджет символов).
- Граф Wiki получает рёбра `related` по косинусу (относительный отбор: top-N
  соседей на запись), а lint — кандидатов на слияние и размер инжекта правил.
- Косинус e5 сжат (релевантное ~0.91, нерелевантное ~0.74), поэтому всюду, где
  нужен порог, применяется относительное правило, а не абсолютное значение.

Деградация: при `provider: off`, отсутствии `@huggingface/transformers`, сбое
воркера или невозможности загрузить расширение плагин возвращается к FTS5;
`llm_memory_status`, `/api/status` и панель Health показывают прогресс индекса и
последнюю ошибку. Переключение бэкенда на `sqlite-vec` требует перезапуска
плагина: загрузка расширений разрешается только при создании соединения.
